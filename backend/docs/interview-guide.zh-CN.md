# Cognitive OS 项目面试讲解与追问手册

整理日期：2026-10-14。依据当前仓库 README、实际 C 实现、测试源码及已保存的基准报告。

使用说明：下面的口述稿介绍项目本身。只有确实由你完成的部分，才能改成“我实现了”。个人分工、开发周期、线上用户和业务收益没有从仓库得到证据，面试时应按真实经历补充。本次整理没有重新执行基准，数据应表述为“仓库记录的测量结果”。

## 1. 项目定位：先把面试官带到正确的问题上

**一句话：用 C11 实现的轻量级 Agent 运行时，把任务生命周期、上下文管理、工具权限和失败恢复交给程序管理，让大模型负责语义理解和规划。**

“认知操作系统”是架构类比。它运行在 Windows/Linux/macOS 上，是用户态应用，不是内核、不提供硬件级内存隔离，也不是自行训练的大模型。

推荐讲解顺序：问题 → 一次任务的链路 → 两三个核心设计 → 验证结果 → 当前限制。不要按目录把所有模块依次报一遍。

| 面试方向 | 优先展开 | 次要展开 |
| --- | --- | --- |
| C/C++、系统研发 | 调度器、协程、对象生命周期、锁、跨平台抽象 | 文件快照、故障恢复 |
| 后端、基础架构 | 状态所有权、背压、持久化、幂等、可观测性 | API、DAG 协作 |
| AI 应用、Agent | 模型与控制面的边界、工具调用、Context MMU、评估 | 安全策略、模型适配 |
| 校招、实习 | 一个完整任务链路、两个亲手实现的难点、可复现实验 | 明确讲清不足 |

## 2. 可以直接练习的口述稿

### 30 秒版本

> Cognitive OS 是一个用 C11 写的跨平台 Agent 运行时。它要解决的是：Agent 长时间执行任务时，不能只靠模型记住状态和遵守约束。所以项目把生命周期、调度、上下文预算、工具权限和文件恢复放到运行时里，模型主要负责理解和规划。我会重点介绍调度、上下文管理和失败恢复这几个设计，以及它们怎么被测试验证。

最后一句根据你的实际贡献改成“我负责的是……”，选两个能读懂源码、能解释失败场景的模块。

### 2 分钟版本

> 这个项目叫 Cognitive OS，是一个 C11 实现的用户态 Agent 运行时。
>
> 背景是工具型 Agent 越做越复杂：它不只要回答问题，还会读写文件、运行命令、调用外部工具，并且需要处理中断、并发和长上下文。如果这些职责都依赖模型每一轮自行维护，系统行为会比较难验证。
>
> 项目的处理方式是分清职责：运行时管理任务状态和动作执行，模型负责理解、推理和规划。一次请求进入调度器后，由状态机驱动认知阶段，规划器生成工具动作，执行前经过权限检查，执行结果回到下一轮，并记录进度和终态。
>
> 我重点准备三个设计。第一是 M:N 协作式调度，用有限 Worker 执行多个任务，优先队列管理待运行任务，协程栈延迟分配。第二是 Context MMU，给记忆提供摘要、概览和全文表示，根据相关性和预算决定哪些内容进入活动上下文。第三是文件快照和任务日志，用于受覆盖文件的恢复以及进程重启后的中断识别。
>
> 仓库记录了确定性本地负载下的规模测试、Context 压力测试和真实进程强制终止测试。例如八个工作 Worker、千个注册角色、十万任务的吞吐约为每秒 1.73 万任务。这里角色数不是并发进程数，吞吐也不包含真实模型请求。项目当前的边界包括阻塞 I/O、启发式验证和有限文件回滚，这些是继续完善的方向。

### 5～8 分钟版本提纲

1. **问题，45 秒：** 长任务需要稳定的状态、权限与恢复，不能完全依赖模型输出。
2. **链路，60 秒：** 以“修改一个文件并检查结果”为例，从请求、调度、规划讲到工具执行和日志。
3. **调度，90 秒：** 队列、延迟分配栈、线程亲和、完成回调、历史回收；解释为什么阻塞调用仍占 Worker。
4. **Context，90 秒：** 规范记录与活动上下文分离，表示层级、预算、晋升/驱逐、原文恢复。
5. **可靠性，90 秒：** 工具边界权限检查、文件快照、进程中断识别、显式重放，以及不能保证的部分。
6. **证据和取舍，60 秒：** 说清负载、样本、指标；给出最想补齐的一个问题。

## 3. 用一个请求讲清架构

例子：“读取配置，把一个字段改为新值，再检查文件能否解析。”

```text
CLI / HTTP / Web 控制台
  → 创建 Task，交给 Scheduler
  → Worker 启动或恢复任务协程
  → 状态机执行认知阶段
  → 召回记忆、构建上下文，LLM 生成工具计划
  → 对实际工具调用做策略检查
  → 执行 file_read / file_edit 等工具
  → 在满足配置和覆盖条件时捕获修改前文件
  → 汇总工具结果、VERIFY、后续规划或结束
  → 保存任务终态、进度和 trace
```

这里是帮助口述的简化链路，不代表所有请求都会启用事务。认知循环的多轮行为位于 reasoning 层，不能只看 state_machine 的单次阶段遍历。

实际 `state_machine.c` 的状态是 RECEIVE、UNDERSTAND、REASON、PLAN、ACT、VERIFY、LEARN，以及 DONE/FAILED。README 中 RECALL、POLICY CHECK、SNAPSHOT、COMMIT/ROLLBACK 是概念步骤，并非全部是独立枚举状态。

| 模块 | 管理什么 | 阅读入口 |
| --- | --- | --- |
| Scheduler / Task | ID、就绪队列、Worker、取消、终态和历史 | `src/runtime/scheduler.c`、`task.c` |
| Reasoning / Planner | 模型规划、动作循环、上下文和执行衔接 | `src/cognition/reasoning.c`、`planner.c` |
| Memory / Context | 规范记忆、检索、活动表示与预算 | `src/memory/record.c`、`src/context/mmu.c` |
| Policy / Tools | 是否允许实际动作，分发工具 | `src/runtime/policy_engine.c`、`src/action/tools.c` |
| Tx / Snapshot | 本轮工具结果、文件原始内容和恢复 | `src/tx/tx.c`、`src/snapshot/snapshot.c`、`cow.c` |
| TaskLog / Flow | 持久化生命周期、协作依赖 | `src/runtime/tasklog.c`、`flow.c` |
| Trace | 带 task ID 的阶段和耗时证据 | `src/infra/trace.c` |

上表路径均相对于 `backend/`。

## 4. 调度与并发：最容易被连续追问的部分

### Q1：M:N 是什么意思？与线程池有什么不同？

M 个任务协程映射到 N 个 OS Worker 线程。线程池限制执行线程，协程可以保存任务调用栈，在 yield 后继续执行。这里是协作式切换，不是抢占式调度。

**继续追问：是不是有协程就能支持百万并发？**

不能。百万任务测试是累计提交并完成百万任务。排队任务尚未分配协程栈；已启动而未完成的协程仍占资源。累计任务规模、活动任务数、同时执行线程数是三个指标。

### Q2：为什么使用堆？复杂度是多少？

就绪队列按 `(priority, id)` 排序：priority 数值越小越先取出，同优先级按 ID。二叉堆插入/弹出为 O(log n)，避免每次取队首都搬移大数组。历史维护仍存在扫描和 memmove，不能宣称整个调度器所有操作都是 O(log n)。

### Q3：协程栈什么时候创建？

Worker 第一次取出任务时懒创建，默认约 256 KiB，完成后释放。收益是大量尚未启动的排队任务不用提前分配栈。它没有消除运行中协程的栈成本，也不提供栈无限增长。

### Q4：yield 后可以被其他 Worker 接手吗？

当前实现保留线程亲和。每个 Worker 有自己的 yield 队列，续体回到所属线程，以符合当前 ucontext/Fiber 封装的执行约束。没有实现可迁移续体或 work stealing。

### Q5：调度公平性如何？会饿死任务吗？

不能保证严格公平。当前 Worker 优先处理自己的 yield 队列，然后才取全局堆；全局队列也没有优先级老化。持续 yield 的任务以及持续进入的高优先级任务，都值得用专门压力场景检查。

改进思路：限制连续续体执行次数，交替服务全局队列，加入 aging；在改进前测量各类任务等待时间。

### Q6：调用 LLM、Shell 时，Worker 会不会被阻塞？

有协程不意味着底层 I/O 全部异步。当前同步调用可能阻塞所属 Worker。任务间的 yield 是检查点，不是自动把网络和进程等待转换成非阻塞 I/O。

如果生产目标是大量等待型任务，下一步应考虑非阻塞 I/O、独立阻塞执行池和限流，测模型延迟下的有效并发。以上是改进方向，不是当前完成能力。

### Q7：取消和超时怎么实现？

任务有取消标记和时间检查，执行链路在检查点响应；不是强行终止 C 线程。调度器的超时检查使用 `started_ms`，因此不要把这个指标称为包含排队的完整请求 deadline。阻塞调用能否及时取消，还要看具体后端。

### Q8：并发读任务时为什么需要引用/借用机制？

历史回收可能释放已完成 Task，HTTP 查询和完成回调不能拿着悬空指针。当前回收检查 `references`、`borrowed`、`completed`；完成回调结束后才将对象标成可回收。

回答重点是“读者生命周期和对象回收如何协调”，不能只说“加锁了”。

### Q9：锁如何使用？为什么回调放在锁外？

Scheduler 锁保护队列、活动计数等共享状态，进度内容有独立锁。runner、协程执行和完成回调不持有调度器大锁，避免把长时间操作和可重入回调放进临界区。仍需检查锁顺序、共享标记读写和后端线程安全，不能据此宣布没有数据竞争。

### Q10：背压如何做？

实现有 `max_active`、最大 Worker 和拒绝计数，可以限制活动任务。构造参数允许 `max_active=0`，所以不能说所有配置默认都有有限队列。部署时要明确容量，再定义拒绝、重试和客户端退避。

## 5. Memory 与 Context：要讲清表示、存储和预算

### Q11：Memory 和 Context 为什么分开？

Memory 保存能长期保留、检索和更新的记录；Context 决定本次给模型提供什么。记住某条信息，不等于每轮都把它全文发送给模型。

### Q12：L0/L1/L2 与 HOT/WARM/COLD 是什么关系？

L0/L1/L2 是内容表示层级：短摘要、带属性的概览、完整正文。HOT/WARM/COLD 是驻留状态。不要把“全文精度”与“是否已物化缓存”混成同一个概念。

当前 L0/L1 通过确定性截取和属性拼接生成，不是每条都调用模型总结。它们有损，原文必须从规范记录恢复。

### Q13：选哪些记忆进入上下文？

MMU 使用相关性、重要性、置信度、效用、时间新近性、显著性和 scope 等信号评分。默认相关性权重 0.35，其他权重见 `ctx_mmu_config_default()`。有候选数、全文 top-k 和预算约束。

这些权重是启发式配置，不能称为经过训练的最优策略。可以通过检索命中率、答案质量、token 成本和原文恢复次数做消融评估。

### Q14：为什么不直接用 LRU？

最近访问不一定最有价值。任务约束、重要事实和相关证据可能很久没有访问，仍需要保留。多因素评分允许考虑任务语义；代价是调参和评估复杂度增加。

### Q15：token 怎么数？中文准确吗？

当前估计是 `(strlen(s)+3)/4`，根据 UTF-8 字节长度近似计算，未接入各模型真实 tokenizer。中文、代码和特殊格式可能存在误差。因此只能叫估算预算，不能保证真实请求严格不超过模型 token 上限。

改进：模型 tokenizer、为系统指令/工具 schema/输出预留预算、对整条请求最终校验。

### Q16：上下文预算限制了整个进程内存吗？

没有。规范正文、表示缓存、JSON 序列化、协程栈和工具结果都可能占 RAM。驱逐 MMU 表示并不一定释放规范正文。仓库记录的 1 GiB 规范内容压力测试峰值 RSS 约 3197 MiB，正好说明这两个指标不能混用。

### Q17：摘要丢掉关键数字怎么办？

把摘要作为检索线索，决策或核验时恢复原文，并保留来源。可以考虑固定保留约束字段、数值和引用，但这是改进方案。原文长度和哈希校验只能证明正文恢复完整，不能证明摘要的语义充分。

### Q18：向量检索是什么实现？是训练出来的 embedding 吗？

向量存储是内存中的余弦相似度检索。本地 embedding 使用 hashing trick 词袋、中文字符 bigram 和 L2 归一化，也支持远程 OpenAI 兼容 embedding 接口。

本地方案离线、确定性、轻量，但不是预训练语义模型；近义表达和跨语言匹配能力有限。当前向量检索也不能包装成百万级 ANN 索引。

### Q19：记忆会不会把失败结果当成事实？

需要区分观察、结论和执行状态，只有满足完成条件的结果才能升级为可靠经验。仓库有 incomplete-run memory gate 的测试。面试时还应承认：门禁可以减少污染，但工具成功或任务 DONE 都不自动证明内容正确。

### Q20：多会话怎样避免串记忆？

从 session、scope、共享记忆开关和检索读写路径解释边界。项目允许共享记忆策略，因此不是所有内容天然隔离。逻辑会话隔离也不等于进程级、租户级安全隔离。

## 6. 文件事务与恢复：最能体现工程判断的部分

### Q21：这里的事务能称为 ACID 吗？

不宜。Tx 汇总工具执行结果，结合文件快照进行提交/恢复；没有证明通用数据库式原子性、隔离性和断电耐久性。尤其 Shell、SSH、网络 API 的副作用不能靠文件恢复自动撤销。

### Q22：文件快照怎么实现？COW 是内核页级写时复制吗？

不是。修改前读取被覆盖文件的原始内容，按内容哈希保存到内容存储，manifest 记录路径、原内容哈希、是否原本存在等信息。相同内容可以复用已有存储对象。

它是应用层内容存储和文件快照，不是操作系统虚拟内存页的 COW。

### Q23：原来不存在的文件怎么回滚？

manifest 区分“原来存在”与“原来不存在”。恢复已有文件时取原内容；恢复新建文件对应的原状态时删除它。必须同时讨论目录、权限、二进制和恢复失败等边界，不能只演示文本覆盖。

### Q24：所有 file_write 都会被快照保护吗？

不会。`tx.c` 对 Git 管理的 workspace 或路径跳过自动捕获；写目标提取只覆盖 `path` 和 `files` 字段，最多 16 个候选路径；快照默认跳过超过 64 MiB 的文件，可用环境变量调整。

所以不能说“全部文件修改自动可回滚”。还要核对是否启用事务、工具是否标记写入、目标是否真正覆盖、捕获是否成功。

### Q25：Git 管理的目录跳过快照，Git 会自动回滚吗？

不会。Git 提供版本工具不等于运行时已经自动保存和恢复未提交状态。当前 Tx 的 Git 跳过逻辑不能作为自动撤销承诺。

改进可以是任务独立 worktree、受控 patch、保存原有工作区状态，但应避免破坏用户原本的未提交修改。

### Q26：快照哈希有没有碰撞？存储线程安全吗？

当前内容地址是 64 位 `hash64`。不能宣称碰撞不可能；更强实现应校验长度/内容或使用更强摘要。

`cow_put()` 返回静态字符缓冲区，函数自身没有锁。并发安全依赖调用方隔离/同步；并发共用时值得改为调用方输出缓冲区，并验证内容写入的竞争。

### Q27：二进制文件能完整恢复吗？

应承认当前限制：`cow_get()` 用 `strlen()` 返回长度，嵌入 NUL 的二进制内容不能据此正确计长。不能把文本 fixture 的成功外推为任意二进制文件恢复成功。

改进需要长度感知的文件读取和存储接口，并增加包含 NUL 的恢复用例。

### Q28：VERIFY 到底验证了什么？

`evaluator_verify()` 是宽松启发式：没有动作可通过，有动作时至少一个动作成功就可能通过；不是完整目标验证器。`tx_validate()` 检查累计工具成功标记，也不是自动运行用户的验收标准。

因此 DONE 应理解为运行链路终态，不能直接等同业务目标完成。更强方案是任务专用后置条件，比如文件解析通过、目标字段一致、测试通过和交付物存在。

### Q29：进程崩溃后怎么知道任务中断？

持久化任务生命周期，重启扫描最新非终态并标为 INTERRUPTED，恢复任务 ID 分配位置，避免与历史重复。内存 Task 与磁盘日志的状态是分离的。

当前文档记载日志超过 32 MiB 解析上限时明确失败，不能静默从 ID 0 重新开始。这也是当前恢复扩展性限制。

### Q30：会自动重试吗？如何保证 exactly-once？

崩溃演示通过显式 resume 重放幂等文件覆盖，不自动重放任意外部动作，不保证 exactly-once。

关键不确定窗口是：外部操作已经成功，但本地尚未写成功日志就崩溃。重启后无法仅凭本地状态确认是否重做。改进通常需要服务端幂等键、结果查询和补偿机制；没有对端支持时不能凭重试次数解决。

### Q31：怎么验证崩溃恢复？

等待任务 RUNNING 且快照可用 → 强制结束整个 Runtime 进程 → 相同状态目录重启 → 检查 INTERRUPTED → 恢复快照并核对文件 → 显式重放到 DONE → 提交后续任务。

Windows 使用 TerminateProcess，POSIX 测试使用 SIGKILL。Worker 是线程，所以不是“单独 kill Worker-3 后进程继续”的故障隔离测试。

## 7. 安全、模型与扩展

### Q32：Prompt 里写禁止操作为什么不够？

模型输出不应直接获得权限。运行时应对实际工具调用进行检查，拒绝的动作不能被执行。项目在 reasoning 和工具分发路径都有相关检查；面试时优先解释最终工具入口的执行边界。

这是降低违规动作发生概率的工程机制，不是“解决了所有 prompt injection”。允许的工具仍可能拥有过大的能力。

### Q33：策略匹配规则是什么？默认安全吗？

精确工具名匹配优先于 `*`；同等精确度最后一条匹配规则生效。显式 ask 通过回调确认，否则拒绝。完全没有规则时默认 allow；已有规则却无匹配时返回 ask，再由调用链处理。

因此不能说当前策略引擎无条件 default deny。生产强化应明确通配拒绝、允许列表以及 ask 的最终处理语义。

### Q34：允许 Shell 后，文件工具的权限还有意义吗？

必须承认 Shell 是强能力入口。只限制 file_write 不能限制 Shell 写文件；工具名级策略也不足以表达所有命令参数和路径风险。需要执行器权限边界、路径约束、网络限制和隔离环境共同约束。

当前逻辑 sandbox、FileTracker、WASM 扩展等能力应按具体实现介绍，不能统一叫完整 OS 安全沙箱。原生动态插件尤其不能视为与 WASM 相同的信任边界。

### Q35：密钥如何避免进入模型和日志？

模型配置密钥保留在后端；项目还有 secret boundary、检测及 SSH 密码脱敏路径。说明检测发生在哪个入口、哪些输出经过脱敏、哪些存储仍含业务文本。

trace span 不记录 prompt、工具参数和工具输出，但任务 journal 可有任务输入/答案等其他字段。不能将“trace 不含正文”说成“所有日志都没有敏感数据”。

### Q36：模型无关具体指什么？

通过统一接口适配 mock、OpenAI 兼容和 Anthropic 协议，封装请求、结果、工具调用和流式事件。模型适配降低耦合，但不同模型的 schema 遵循、上下文能力、工具调用质量仍需分别测试。

### Q37：SSE 分块是不是一块就是完整 JSON？

不能这样假设。网络块、SSE 事件和模型增量字段是不同边界，需要缓存、按事件分隔、解析字段，再累计文本或工具参数。准备阅读 `src/llm/sse.c` 和对应流式测试，能解释断流及未完成工具参数如何处理。

### Q38：MCP、Skill、Plugin 有什么区别？

Skill 提供指令和流程；MCP 连接外部工具服务；Plugin 扩展本地运行能力。它们的安装、权限和失败边界不同。MCP 服务仍可能依赖 Node/Python 等外部环境，所以“核心 C 运行时可独立构建”不能扩大为所有功能零依赖。

### Q39：多 Agent 等于多个模型并发吗？

注册 Agent 首先是命名角色与配置，不等于独立进程。Flow 表达任务依赖，用 Kahn 算法检查环并分层，同层节点通过线程并行执行。当前常量限制 64 个节点、最大并行 8。

不要把 Flow 的分层线程执行与 Scheduler 的协程机制说成完全相同的执行路径。

### Q40：一个分支失败会怎么样？

依赖它的后继应 blocked，独立分支可继续。引用上游结果也会建立依赖，不能只检查显式 edges。准备解释不存在的引用、自依赖、环、重复边和截断后的结果。

当前按层执行存在屏障：某个长节点可能拖延下一层。依赖就绪即调度可以改善利用率，但属于后续设计。

## 8. 性能与评测：每一个数字都要带边界

### Q41：吞吐数据到底测了什么？

仓库记录的 Windows 本地确定性负载：8 个工作 Worker，每任务 64 次 Context 读取和角色指令拼接，聚合 Context 8 MiB，另有 2 个空闲 Runtime Worker。注册角色数不等于线程数；不包含生产模型推理和网络延迟。

| 规模 | 仓库记录结果 | 应怎样解读 |
| --- | --- | --- |
| 1000 角色、10 万任务 | 约 17,328 任务/秒；排队 P99 0.376 ms；峰值 RSS 22.57 MiB | 固定轻量负载下的调度观测 |
| 1000 角色、100 万任务 | 约 13,835 任务/秒；排队 P99 14.790 ms；峰值 RSS 77.92 MiB | 吞吐下降约 20%，不能声称线性扩展 |
| 1 GiB 规范 Context | 峰值 RSS 3197.01 MiB，原文校验通过 | 测存储/物化/恢复，没有发送 GiB prompt |
| 强杀整个进程后恢复 | 崩溃到显式重放 DONE 约 591.759 ms | 当前 fixture 单次测量，不是恢复 SLO |

### Q42：为什么要看 P99，而不是只有平均值？

少数积压会被平均值掩盖。应同时看吞吐、排队延迟分位数、队列峰值和 RSS。排队时间不是端到端完成时间；人为阻塞 Worker 的积压试验也不能与正常提交混算。

### Q43：重复次数足够吗？

规模数据取三轮中位数，峰值 RSS 取该组最大值；Context 大内存布局各一轮，实际驱逐次数很少，崩溃演示也是特定用例。能说明这些场景跑通，不能建立生产尾延迟承诺。

### Q44：如何证明运行时让模型成绩提高？

单个成绩不足以因果归因。需要相同模型、工具、数据集、采样和预算下的对照/消融。浏览器工具、OCR、Prompt 和评估环境都可能改变分数，不能全部归功于调度器或 Memory OS。

### Q45：GAIA / SWE-bench / BFCL / WebArena 是官方完整评测吗？

仓库报告区分得很重要：GAIA 2023 validation 是 165 题；SWE-bench Verified 是 11 题 mini；BFCL-style 是自建 22 例；WebArena-style 是 6 个任务。后两项不能说成官方完整榜单。

SWE-bench 报告 8/11，并记录同 11 题 Docker 隔离重跑为 5/11；应同时说明运行差异和小样本限制，不能与完整官方测试集分数直接比较。这里引用的是仓库报告，不是本次独立核验的排行榜结果。

### Q46：测试怎么组织？

按性质解释：核心 C 单元/集成测试检查队列、协程、策略、快照、记忆等；mock 模型保证确定性链路；Python/浏览器端到端测试验证恢复、依赖和 UI；真实模型评测检查任务能力但存在随机性。

例子入口：`tests/test_all.c`、`test_runtime_benchmark.py`、`test_crash_recovery_e2e.py`、`test_flow_dependencies_e2e.py`、`test_stream.c`。本手册整理只检查源码和报告，没有声称当前所有测试已重新通过。

## 9. C、跨平台与设计取舍

### Q47：为什么选 C？Python 不行吗？

项目目标包括轻量部署、可控对象生命周期、跨平台 OS 抽象和嵌入式控制台，C 与这些目标匹配。但模型请求主导的任务延迟未必因换语言显著降低。

代价是内存安全、字符串/JSON 处理、协议维护和开发效率。回答要体现目标与代价，避免“C 一定比 Python Agent 好”。

### Q48：内存管理怎么避免出错？

解释 owned/borrowed、new/free、返回字符串由谁释放，以及完成回调期间对象不能回收。`tx_begin()` 用 `sizeof(*tx)`，源码记录了局部变量与 typedef 同名时 `sizeof(tx)` 可能只得到指针大小的风险，这是可讲的具体 C 细节。

仍存在需要加强的错误路径和分配检查。生产准备应使用编译警告、内存/线程检查工具和故障注入，但不要说这些工具都已在当前环境跑过。

### Q49：Windows/Linux 的差异怎么处理？

线程、协程、文件、进程、socket 和时间放在 OS 抽象层；Windows 使用 Fiber，Linux 使用 ucontext。还需处理 Unicode 路径、进程终止、信号和 Shell 差异。跨平台意味着同一接口有多实现，不能保证所有工具行为天然一致。

### Q50：这套系统目前最大的短板是什么？

按岗位选一个深入讲：

- 系统方向：同步阻塞 I/O 限制 Worker 利用率，调度公平性需要额外验证。
- AI 方向：VERIFY 仍是宽松启发式，需要任务后置条件；本地 embedding 和 token 估算较粗。
- 可靠性方向：快照覆盖、二进制长度、捕获错误、外部副作用幂等与日志耐久性需要加强。

回答模板：“当前实现是什么 → 哪个反例会失败 → 为什么现有测试没覆盖 → 我会怎样改 → 用什么测试验收。”

## 10. 两个适合展开的技术故事

以下是仓库中可支撑的技术故事结构。没有亲历时，称为“项目的设计/测试”，不要伪造自己的排障经历。

### 故事 A：调度规模与历史内存

- 问题：累计任务增长时，队列操作和终态历史可能持续消耗资源。
- 设计：堆队列、延迟协程栈、有限历史、引用保护和回调后回收。
- 证据：任务接收/完成守恒，结束队列和 active 归零，测 RSS 与排队分位数。
- 反思：百万任务测试的 RSS 包含完整性数组；历史清理仍有扫描成本，且吞吐/尾延迟随规模恶化。

### 故事 B：把“能重启”变成可验证的恢复链路

- 问题：重启服务不代表中断任务及文件状态恢复正确。
- 设计：生命周期日志、INTERRUPTED、ID 恢复、文件快照和显式 resume。
- 证据：强杀整个进程，检查中断状态，恢复文件并核对，再重放和提交后续任务。
- 反思：幂等文本覆盖不能证明任意外部动作 exactly-once，也不能证明断电耐久性。

## 11. 简历写法与不能说满的地方

项目描述示例，个人贡献按事实调整：

> Cognitive OS：基于 C11 的跨平台 Agent 运行时，提供任务生命周期、M:N 协作式调度、上下文分层管理、工具策略检查及文件快照恢复，支持模型协议适配和 Web 控制台。

可选贡献句：

- 实现/优化基于优先堆的任务调度及有限历史回收，通过确定性负载验证任务完整性、队列收敛和资源占用。
- 实现/完善 Context 分层表示与预算控制，通过驱逐、重新物化和磁盘重载核对规范正文完整性。
- 实现/完善任务日志和中断恢复链路，以真实进程终止验证中断识别、文件恢复与显式重放。

没有亲手完成就删除“实现/优化”，改成“参与”并明确范围。不要填不存在的用户规模、节省成本比例或个人开发周期。
