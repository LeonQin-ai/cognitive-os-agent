# 模型说要调用工具，Runtime 如何接住：协议解析、分页阅读与附件处理

> 一次工具调用失效，有时不是工具坏了，而是模型计划没有被正确解析；一次源码总结不完整，也可能是系统把“读了第一页”误当成“读完”。可靠执行需要把输入格式和完成证据都处理清楚。

这是 [Cognitive OS](https://github.com/LeonQin-ai/cognitive-os-agent) 技术系列第 5 篇，选三个实际工程问题说明模型输出如何进入执行链路。

## DSML 出现在答案里，却没有工具执行

用户曾遇到这样的记录：模型输出了多段 DSML 工具调用，界面却显示“本次未调用工具”。模型表达了动作，Runtime 没有把该格式还原为合法计划，自然也就没有真正执行。

Planner 因此需要兼容项目覆盖的 JSON、标签和 DSML 形式，将工具名与参数转换为内部动作数组。重要的不是“能从字符串中找到一个工具名”，而是整批计划中的每个动作都能正确恢复。

一个危险的折中是：某一段解析失败，就丢弃它，只执行剩余部分。这样任务会在用户不知情时变成另一个任务。项目对相关格式采用整批校验：非法或不完整结构需要明确失败，不能静默遗漏动作。

兼容解析也有边界。支持若干协议变体，不等于可以执行任意模型文本。结构合法之后，仍需工具查找、参数处理、策略与实际执行。

## 文件读取成功，不代表完整阅读成功

大型源码通常分多页读取。假设第一段已经成功返回，模型随即写出“项目完整分析如下”，Runtime 如果只看最后一句，就会提前结束。

项目的文件阅读链路会提供或追踪 `offset_bytes`、`next_offset_bytes` 和 EOF 等信息。对明确要求完整阅读的任务，未到 EOF 的文件属于尚未完成的工作；目录枚举也不能替代源码阅读。

```text
读取 source.c 的第一段
 → 发现还有 next_offset_bytes
 → 继续读取后续字节
 → 核对 EOF
 → 根据完整观察整理结果
```

偏移使用字节口径，后续页应沿工具返回的偏移继续，而不是自行根据显示行数推算。模型请求过大的页长时，系统还需要明确说明实际截断值，避免“请求读很多”和“实际只拿到一部分”之间出现静默差异。

相关 HTTP 回归会把关键证据放在文件末段，再确认模型实际拿到该证据。只检查工具返回过 success，无法覆盖这个问题。

## 支持附件，需要区分三层能力

用户上传图片、Word、PPT、PDF 或视频时，至少存在三个不同阶段：接收与保存文件、提取可用表示、让模型理解这些表示。

项目在附件链路中记录类型及解析元数据；文档可提取文本，多模态内容可形成图片或视频采样帧等输入。视频帧理解属于采样观察，不能等同于完整逐帧理解，更不能据此宣称音轨转写、每个动作识别都已具备。

实际效果依赖格式、可选解析依赖和所用模型。扫描件可能需要 OCR，图片输入需要兼容视觉能力的模型接口，损坏文件或不支持的格式应该返回诊断信息。文件扩展名出现在列表里，不是解析质量的证明。

另一个边界是请求时间。图片解析或视觉模型迟迟不返回时，用户需要看到阶段、超时与错误，而不是无限等待。相关回归通过慢速本地 provider，验证超时后能结束，并能继续下一次正常请求。

## 怎样观察真实执行

我希望演示可以回答：模型发出了什么动作？Runtime 解析出了几个？实际工具是否调用？分页是否结束？失败是哪一层产生？

在构建 CLI 后，可从这些回归进入：

```bash
cd backend
python tests/test_dsml_e2e.py
python tests/test_source_read_e2e.py
python tests/test_vision_wait_e2e.py
```

这些用例使用本地模型 fixture 和真实 Runtime/API，验证协议与控制流；它们没有测量生产模型对所有文件的理解准确率。
